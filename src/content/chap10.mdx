## 1. CI（継続的インテグレーション）とは？

CI環境を構築すると、誰かがGitHubにコードをPushしたり、Pull Requestを作成したりするたびに、クラウド上のサーバーが自動でDockerコンテナを立ち上げ、これまで作ってきた `run_all_tests.sh` などを実行してくれます。

## 2. GitHub Actions のワークフロー記述

`.github/workflows/test.yml` というファイルを作成するだけで、GitHubが自動でテストを代行してくれます。第2章で作ったDockerイメージをそのまま使えるのが強みです。

```yaml
name: Sonar DSP CI

on: [push, pull_request]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    container:
      # 第2章で作ったDockerイメージをDockerHubやGHCRに上げておく
      image: myrepo/cpp-test-env:latest 

    steps:
      - name: コードのチェックアウト
        uses: actions/checkout@v3

      - name: CMakeビルド (ASan有効化)
        run: |
          mkdir build && cd build
          cmake -DCMAKE_BUILD_TYPE=Debug ..
          make -j4

      - name: C++ 単体テストの実行 (gtest)
        run: cd build && ctest --output-on-failure

      - name: Python 数理評価テストの実行 (pytest)
        run: pytest tests/

      - name: 失敗時のグラフ画像を保存 (Artifact)
        if: failure()
        uses: actions/upload-artifact@v3
        with:
          name: error-plots
          path: error_report.png
```

## 3. もう「壊れたコード」はマージできない

この設定により、誰かがテストを通っていない壊れたコードをPushすると、GitHub上で「バツ印（❌）」が付きます。さらに、第7章で作った**エラー時のグラフ画像**がGitHub上から直接ダウンロードできるようになります。
