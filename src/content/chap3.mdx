## 1. そもそも「CMake」とは何か？（なぜg++やMakeだけじゃダメなのか）

C++の勉強を始めた人が必ず抱く疑問があります。  
**「C++のビルドなら `g++ main.cpp` でいいのでは？ なぜCMakeやMakeなんてツールが必要なの？」**

1つのファイルだけなら `g++` コマンド手打ちで十分です。しかし実際の業務アプリは**数十〜数百個の `.cpp` ファイル**で構成されます。

ファイルを1文字直しただけで、毎回すべてのファイルをゼロから再コンパイルしていたら、**ビルド待ちで毎日何時間も溶けてしまいます**。  
そこで生まれたのが、**「変更されたファイルだけを賢くコンパイルする仕組み」**です。

### 🏢 3つのツールの決定的な役割分担（建築現場のたとえ）

ビルドを「建物の建設」にたとえると、それぞれの役割が一撃で理解できます。

* **職人（コンパイラ: `g++`, `clang++`）**  
  指示された1つの `.cpp` ファイルを、機械語の部品（`.o` オブジェクトファイル）に翻訳する実作業員。
* **現場監督（ビルド自動化ツール: `Make`, `Ninja`）**  
  「今回はどのファイルが更新されたか」をチェックし、「更新された部品だけ職人に作らせて、最後に1つに結合しよう」と現場の段取りを仕切る。
* **指示書の自動作成係（メタビルドツール: `CMake`）**  
  現場監督に渡す「超複雑な段取り表（Makefile）」を、人間が書いたシンプルな希望レシピ（`CMakeLists.txt`）から**全自動で作成してくれる優秀な秘書**。

```
【人間が書くもの】           【CMakeが自動作成】               【Makeが段取り良く実行】
CMakeLists.txt (簡単な希望) ───> Makefile (複雑な段取り表) ───> 必要な分だけg++で高速ビルド！
```

### 📌 なぜ人間はMakefileを手書きしなくなったのか？

実際のコードを見比べてみましょう。「同じこと（ライブラリ作成）」をするのに、人間が書く内容がこれだけ変わります。

#### ① コード量の違い

```makefile
# 【昔】手書き Makefile：コマンドや依存関係を1行ずつ泥臭く指示する
CXX = g++
CXXFLAGS = -Wall -std=c++17 -Iinclude
OBJS = src/sonar_filter.o src/math_utils.o

# ★インデントは絶対に「タブ文字」！スペースだと構文エラーで止まる
sonar_core.a: $(OBJS)
	ar rcs $@ $^

src/sonar_filter.o: src/sonar_filter.cpp include/sonar_filter.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

src/math_utils.o: src/math_utils.cpp include/math_utils.hpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
```

```cmake
# 【現代】CMakeLists.txt：人間は「やりたい目的」だけをシンプルに書く
# ※「sonar_core」は本チュートリアルの題材（ソナー信号処理）に応じた「自作ライブラリ名」です（一般的な予約語ではありません）
add_library(sonar_core
    src/sonar_filter.cpp
    src/math_utils.cpp
)
target_include_directories(sonar_core PUBLIC include)
```

#### ② 昔の手作業 vs 現代の自動化の決定的な違い

| 困りごとのポイント | 昔（手書きMakefileの時代） | 現代（CMakeに任せる時代） |
| :--- | :--- | :--- |
| **依存関係の追跡** | ヘッダー（`.h`）の更新関係を手作業で書かないと、**コードを直したのに再コンパイルされない恐怖のバグ**に直面 | `#include` を**CMakeが自動解析**して段取り表に落とし込んでくれる |
| **文法エラーの罠** | インデントにスペースが混ざると `missing separator` で即死（タブ文字必須の罠） | スペースでもタブでも自由 |
| **OSの壁（移植性）** | Linux用に書いたMakefileは、WindowsのVisual StudioやMacのXcodeでは使えない | 1つのレシピから、**Linux用MakefileもWindows用VSソリューションも全自動生成** |

> 💡 **CMakeとMakeは「ライバル」ではなく「協力関係」！**  
> 「CMakeを使ったらMakeは不要になるの？」と勘違いされがちですが、そうではありません。  
> **「人間がCMakeに希望を伝え、CMakeが賢いMakefileを作り、Makeがそれを忠実に実行する」** という二人三脚です。  
> 開発者は `cmake -B build` でMakefileを作らせ、その裏で `make`（またはNinja）が実際のコンパイル作業を担っています。

**結論：開発者は `CMakeLists.txt` の書き方だけ覚えればOKです！**

## 2. そもそも「CTest」とは何か？（なぜテストランナーが必要か）

テストコードが増えてくると、`test_math`、`test_filter`、`test_network` のように**テスト用の実行ファイルが何十個も作られる**ようになります。

これを毎回手動で1つずつ `./test_math`, `./test_filter` ... と叩いて回るのは不可能です。

> 📌 **CTestとは？**  
> CMakeに最初から標準搭載されている**「テスト一括自動実行＆結果集約マネージャー」**です。

* **一括実行**: 登録された全テストを1コマンドで並列実行する。
* **合否判定サマリー**: どこで何個のテストが落ちたかを「100% tests passed, 0 tests failed」のように即座に集計レポートする。
* **CI/CD連携**: GitHub Actionsなどの自動パイプラインでは、`ctest` の終了コード（0なら成功、1なら失敗）を見てデプロイの可否を自動判定する。

## 3. 「ライブラリ」と「テスト」を分離する設計思想

テストしやすいC++設計の鉄則は、**「`main()` 関数を持つ実行ファイルにすべての処理を書かない」**ことです。

* **コアロジック**: ライブラリ（静的ライブラリ `.a` や共有ライブラリ `.so`）としてビルドする。
* **本番アプリ**: コアライブラリをリンクして `main()` から呼び出す。
* **テストアプリ**: 同じコアライブラリをリンクして、テストフレームワーク（GoogleTest）から関数を直接テストする。

> 💡 **コラム：「`sonar_core`」って何？ 一般的な用語？**  
> コード例に出てくる `sonar_core` は、CMake の標準機能や予約語ではなく、**本チュートリアルの題材（ソナー信号処理システム）に合わせて私たちが自由に命名した「自作ライブラリ名」**です。  
> CMakeの構文は `add_library(<ライブラリ名> <ソースファイル...>)` となっており、ご自身のプロジェクトでは `game_engine` や `network_core`、`sensor_driver` など、好きな名前に置き換えて使用します。

## 4. 実務で使える CMakeLists.txt のテンプレート

プロジェクトのルートに配置する `CMakeLists.txt` の書き方を見てみましょう。

```cmake
cmake_minimum_required(VERSION 3.14)
project(SonarAutomationLab CXX)

# C++17規格を要求
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# ---------------------------------------------------
# 1. プロダクトコード（コアロジック）をライブラリ化
# ※「sonar_core」は当プロジェクト固有の自作ライブラリ名（任意命名）です
# ---------------------------------------------------
add_library(sonar_core
    src/sonar_filter.cpp
    src/math_utils.cpp
)
target_include_directories(sonar_core PUBLIC include)

# ---------------------------------------------------
# 2. CTestの有効化とテストターゲットの作成
# ---------------------------------------------------
enable_testing() # ★これを書くだけでCTestが有効になる！

# テスト用実行ファイルの定義
add_executable(sonar_test
    tests/test_sonar_filter.cpp
)

# コアロジックとGoogleTestをリンク
target_link_libraries(sonar_test
    PRIVATE sonar_core
    PRIVATE gtest gtest_main pthread
)

# ★CTestにテストとして登録
add_test(NAME AllUnitTests COMMAND sonar_test)
```

## 5. 実行してみよう：CMakeとCTestの基本3ステップ

ターミナルで実際にビルドとテストを回すコマンドは、現代のCMakeでは以下の**3行だけ**です。

```bash
# 1. 設定フェーズ：buildディレクトリを作り、Makefileを自動生成
cmake -B build

# 2. ビルドフェーズ：ソースコードをコンパイル＆リンク
cmake --build build

# 3. テストフェーズ：CTestで全テストを一括自動実行！
ctest --test-dir build --output-on-failure
```

> 💡 **ワンポイントアドバイス**  
> `ctest` に `--output-on-failure` を付けると、**失敗したテストの詳細ログだけを画面に出力**してくれます。何百個もテストがある実務では必須のオプションです。
