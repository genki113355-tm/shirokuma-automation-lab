## 2. そもそも「Docker」とは？なぜC++開発で必須なのか？

### ① 仮想マシン（VM）とコンテナの決定的な違い
「Linux環境を用意する」と聞くと、VirtualBoxやVMwareなどの仮想マシン（VM）を思い浮かべる人も多いでしょう。しかし、両者には決定的な違いがあります。

| 項目 | 従来の仮想マシン (VM) | Dockerコンテナ |
| :--- | :--- | :--- |
| **仕組み** | ハードウェアをエミュレートし、**ゲストOSを丸ごと動かす** | ホストOSのカーネルを共有し、**プロセス単位で隔離空間を作る** |
| **起動時間** | 数十秒〜数分（OS起動待ち） | **0.1秒〜数秒（即座に起動）** |
| **リソース消費** | メモリ数GB、ディスク数十GBを専有 | メモリ数十MB〜、極めて軽量 |
| **可搬性** | 巨大な仮想ディスク（.vmdk）の配布が困難 | **数KBのテキスト（Dockerfile）1つで共有可能** |

### ② Dockerを理解する「3大概念」のメンタルモデル
Dockerを使いこなすために覚えるべき単語は、たったの**3つ**だけです。

```
【1. Dockerfile】        【2. Dockerイメージ】       【3. Dockerコンテナ】
   ［設計図・レシピ］  ──(build)──>  ［金型・冷凍食品］  ──(run)──>  ［実体・動く部屋］
  (テキストファイル)               (静的なスナップショット)          (メモリ上で実行中の空間)
```

1. **Dockerfile（設計図）**: 「ベースはUbuntu 22.04、g++とCMakeを入れて、ソースをコピーしてビルドする」という手順をコード化したテキスト。
2. **Dockerイメージ（金型）**: `docker build` コマンドでDockerfileから作られる「完成品の静止スナップショット」。チームやサーバーに配布するのはこれです。
3. **Dockerコンテナ（実体）**: `docker run` コマンドでイメージから起動した「使い捨ての隔離空間」。テストが終われば跡形もなく消滅させることができます。

### ③ なぜC++エンジニアがDockerを使うと救われるのか？
PythonやNode.jsのようなスクリプト言語と異なり、C++は**OSのシステムライブラリ（glibcやlibstdc++）のバージョンに極めて強く結合**しています。

「先輩のPC（GCC 12）では通るコードが、新人のPC（GCC 9）では内部コンパイラエラーになる」<br/>
「Windowsローカルで動いたバイナリが、本番のLinuxサーバーに持っていくとセグフォ（不正メモリ参照）で落ちる」

こうした**C++特有の泥沼トラブルを根絶する唯一の解**が、「ソースコードだけを共有するのをやめ、**コンパイラとOS環境ごとDockerでパッケージ化して共有する**」というアプローチです。

## 3. 実践：C++テスト自動化用 Dockerfile の記述

それでは、Ubuntu 22.04をベースに、C++のコンパイル（GCC, CMake）、テスト（GoogleTest）、そして後ほど使用するPython（pybind11, NumPy）をすべて詰め込んだクリーンルームを作ってみましょう。

プロジェクトのルートディレクトリに `Dockerfile` という名前のファイルを作成し、以下を記述します。

```dockerfile
# ベースイメージとして軽量かつ安定したUbuntu 22.04を使用
FROM ubuntu:22.04

# 対話的なプロンプトを無効化（tzdataなどのインストールで止まらないようにするため）
ENV DEBIAN_FRONTEND=noninteractive

# 1. 必要なパッケージを一括インストール
RUN apt-get update && apt-get install -y \
    build-essential \
    cmake \
    git \
    libgtest-dev \
    python3 \
    python3-pip \
    && rm -rf /var/lib/apt/lists/*

# 2. GoogleTestのソースをビルドしてシステムにインストール
# （libgtest-devはソースコードのみを提供するため、コンテナ内でビルドが必要）
RUN cd /usr/src/gtest && \
    cmake CMakeLists.txt && \
    make && \
    cp lib/*.a /usr/lib/

# 3. Pythonのテスト用ライブラリをインストール
RUN pip3 install pytest numpy matplotlib pybind11

# 作業ディレクトリの設定
WORKDIR /workspace
```

## 4. docker-compose.yml で起動を簡略化

毎回長い `docker run` コマンドを打つのは大変です。手元のパソコンのフォルダ（カレントディレクトリ）を、コンテナ内の `/workspace` に**同期（ボリュームマウント）**させる設定を `docker-compose.yml` に記述しましょう。

```yaml
version: '3.8'
services:
  cpp-lab:
    build: .
    container_name: shirokuma_cpp_lab
    # ホストのカレントディレクトリをコンテナの/workspaceにマウント
    volumes:
      - .:/workspace
    # コンテナがすぐ終了しないようにプロセスを維持
    tty: true
```

これにより、ローカルのVSCodeでコードを編集すると、コンテナ内のコードも即座に更新されます。**「コードの編集は使い慣れたローカルPCで、コンパイルとテストはクリーンなコンテナ内で」**という、プロが使う最強の開発環境が完成します。

## 5. コンテナの起動と確認

ターミナルを開き、以下のコマンドを実行します。

```bash
# コンテナのビルドとバックグラウンド起動
$ docker compose up -d

# コンテナ内部のbashシェルに侵入
$ docker exec -it shirokuma_cpp_lab bash
```

プロンプトが `root@xxxxxx:/workspace#` に変われば成功です！
試しにコンパイラのバージョンを確認してみましょう。

```bash
root@xxxxxx:/workspace# g++ --version
g++ (Ubuntu 11.4.0-1ubuntu1~22.04) 11.4.0
```
